# 本地开发启动与测试

适用项目：sl-ai-admin；以 Mac / Apple Silicon 开发 Web 管理后台为主。核对日期：2026-11-13。

## 1. 本地需要开哪些软件

| 软件／服务 | 是否需要 | 做什么 |
| --- | --- | --- |
| VS Code 或你常用的编辑器 | 建议 | 打开项目、修改代码 |
| iTerm2／终端 | 必须 | 保持前端和后端开发服务运行 |
| Chrome | 必须有浏览器 | 访问本地页面、查看界面效果和请求 |
| PostgreSQL 17 服务 | 必须 | 保存本地账号、登录会话和业务数据 |
| Node.js、pnpm | 必须安装 | 运行前后端和项目工具，不需要单独打开窗口 |
| Docker Desktop | 可选 | 只有选择 Docker 数据库或构建云端镜像时才需要打开 |
| Prisma Studio／其他数据库客户端 | 可选 | 查看本地数据库表与记录 |
| AWS、Cloudflare 控制台 | 本地开发不需要 | 云端发布时才使用 |
| Xcode／Android Studio | 只开发 Web 时不需要 | 移动端模拟器和原生构建另行配置 |

你当前机器已安装 Node.js `26.13.0`、pnpm `12.16.1`、Homebrew PostgreSQL `17.11`。新配置开发环境时可与 CI 一样选 Node.js 24；包管理器按根目录 `packageManager` 使用 pnpm `12.16.1`。

本次只读检查确认 `localhost:5432 - accepting connections`，说明 PostgreSQL 正在运行。`apps/server/.env`、`apps/web/.env` 已存在，没有读取或改写其中的密码。

**使用现有 Homebrew PostgreSQL 时，不需要为了开发 Web 打开 Docker Desktop，也不需要再创建第二套数据库服务。**

## 2. 每天开发的最短流程

这节适合已经配置过 `.env`、安装过依赖并初始化过本地数据库的你。

### 终端 1：确认数据库，启动后端

```sh
cd /Users/slowcoder/Desktop/sl-ai-admin

pg_isready -h localhost -p 5432

# 如果上面没有显示 accepting connections，再启动数据库服务
brew services start postgresql@17

pnpm dev:server
```

后端启动后会输出：

```text
Server is running on http://localhost:3000
```

这个终端保持运行。服务运行时没有回到命令提示符是正常现象。

### 终端 2：启动前端

新开一个终端标签页：

```sh
cd /Users/slowcoder/Desktop/sl-ai-admin
pnpm dev:web
```

前端地址：<http://localhost:3001>。

### 浏览器：看效果

1. 打开 <http://localhost:3001/login>。
2. 使用本地数据库中的账号登录；没有账号时，在本地页面注册一个。
3. 登录后访问 <http://localhost:3001/dashboard>。
4. GitHub 用户管理页面：<http://localhost:3001/dashboard/github-users>。
5. 修改 Web 页面代码并保存，通常会热更新；修改后端代码，`tsx watch` 会自动重启后端。

`3001` 是管理后台，`3000` 是接口服务。访问 `http://localhost:3000` 只显示 `OK`，这不是后台页面。

默认不必执行 `pnpm dev`：它会启动仓库中多个应用，包括移动端和文档站。只开发管理后台时，分开运行 `dev:server` 与 `dev:web` 更容易看日志、停服务和定位问题。

## 3. 首次启动，或换电脑后的准备

### 3.1 打开项目并检查工具

```sh
cd /Users/slowcoder/Desktop/sl-ai-admin
node --version
pnpm --version
psql --version
```

pnpm 缺失时，先安装 Node.js，再按项目固定版本安装 pnpm：

```sh
npm install --global pnpm@12.16.1
```

如果 `node` 或 `npm` 都不存在，先从 [Node.js 官方网站](https://nodejs.org/)安装 Node.js 24，再开一个新终端。

### 3.2 确认 PostgreSQL

你目前使用 Homebrew PostgreSQL 17：

```sh
brew services start postgresql@17
pg_isready -h localhost -p 5432
```

成功标志：

```text
localhost:5432 - accepting connections
```

这是检查服务是否接受连接，不代表账号密码已经验证成功；后续 Prisma 命令会验证实际数据库连接。

全新电脑还未安装 PostgreSQL 时，可使用：

```sh
brew install postgresql@17
brew services start postgresql@17
```

如果已安装但找不到 `psql` 或 `pg_isready`，在当前终端临时加入路径：

```sh
export PATH="$(brew --prefix postgresql@17)/bin:$PATH"
```

确认有效后，再把同一行加入自己的 `~/.zshrc`。不要覆盖整个配置文件。

### 3.3 核对本地环境文件

已有 `.env` 时，保留现有本地密码和密钥，不要把下面的占位示例直接覆盖进去。

后端文件 `apps/server/.env`，新建时参考：

```dotenv
NODE_ENV=development
BETTER_AUTH_SECRET=REPLACE_WITH_A_RANDOM_LOCAL_SECRET_AT_LEAST_32_CHARS
BETTER_AUTH_URL=http://localhost:3000
CORS_ORIGIN=http://localhost:3001
DATABASE_URL=postgresql://postgres:REPLACE_WITH_YOUR_LOCAL_PASSWORD@localhost:5432/sl_ai_admin
```

- `BETTER_AUTH_SECRET`：本地使用的随机字符串，至少 32 字符；已有值可继续使用。可在本机运行 `openssl rand -hex 32` 生成，再自行填入文件。
- `DATABASE_URL`：用户名、密码、数据库名必须与你自己的本地数据库一致。上面的 `postgres` 和 `sl_ai_admin` 是示例；已有配置可使用自己的库名。
- 密码含 `@`、`:`、`/` 等字符时，URL 中的密码需要做 URL 编码。
- 本地不配置 `DB_AUTH_MODE=iam`，不填写云端 `DB_HOST`。普通本地连接使用 `DATABASE_URL`。

前端文件 `apps/web/.env`：

```dotenv
NODE_ENV=development
NEXT_PUBLIC_SERVER_URL=http://localhost:3000
```

本地 Web 的 `.env` **不要添加 `AWS_API_ORIGIN` 行**。本地浏览器请求和服务端会话检查都应指向本地后端；也不要专门写一个空的 `AWS_API_ORIGIN=` 行。

如果此前在终端用 `export` 设置过部署或调试环境变量，环境变量可能覆盖文件配置。使用干净的新终端，或在准备从 `.env` 加载本地配置前清除旧值：

```sh
unset NODE_ENV DATABASE_URL BETTER_AUTH_SECRET BETTER_AUTH_URL CORS_ORIGIN
unset DB_AUTH_MODE DB_HOST DB_NAME DB_USER
unset AWS_API_ORIGIN NEXT_PUBLIC_SERVER_URL
```

这只清除当前终端的导出值，不会修改 `.env` 文件。之后再启动服务或运行 Prisma 命令，让 Varlock 读取本地配置。

环境文件关系：

| 文件 | 用途 |
| --- | --- |
| `apps/server/.env` | 本地后端地址、数据库连接、鉴权密钥 |
| `apps/web/.env` | Web 调用哪个后端 |
| `packages/db/.env.schema` | 已通过 Varlock 导入 server 的 `DATABASE_*` 配置，一般不另建一套数据库密码 |
| 各 app 的 `.env.schema` | 变量声明和类型约束，不是存放真实密码的地方 |
| 各包自动生成的 `env.ts` | 工具生成的类型文件，不手改 |

`.env` 已在 `.gitignore` 中。本地、测试和云端配置分别使用各自的数据库。

### 3.4 数据库不存在时才创建

如果你已有正常使用的本地数据库，直接跳到下一节。

确认本地数据库用户是 `postgres`，且想新建名为 `sl_ai_admin` 的库时：

```sh
createdb -h localhost -p 5432 -U postgres -W sl_ai_admin
```

按提示在终端输入本地数据库密码，输入时不显示字符是正常的。`-W` 是要求交互输入密码，不要将真实密码写入命令行。

如果提示库已存在，无需再建。如果提示 `role postgres does not exist`，说明新电脑尚未创建这个角色，应使用本机已有的数据库管理员角色，或先创建一个专用于开发的数据库角色，再同步修改 `DATABASE_URL`；不要为匹配示例而重置原有数据库密码。

### 3.5 安装依赖、生成客户端、应用已有迁移

先确认 `DATABASE_URL` 指向刚才的本地库，再运行：

```sh
pnpm install --frozen-lockfile
pnpm db:generate
pnpm -F @sl-ai-admin/db exec prisma migrate deploy
```

三步各自的作用：

1. `install`：安装依赖，postinstall 同时生成 Varlock 类型。
2. `db:generate`：生成 Prisma Client；本身不会创建表或迁移数据。
3. `migrate deploy`：把仓库已经提交的迁移应用到当前本地数据库。

项目目前使用 Prisma 7；不要照 Prisma 8 文档替换这些命令。首次拉代码，或别人新增迁移后，不能只安装依赖就启动。

迁移通过后，按第 2 节分别启动后端与前端。正常日常开发不需要每次重新安装依赖和迁移。

## 4. 怎样确认本地完整跑通

新开一个终端检查接口：

```sh
curl --fail --silent --show-error http://localhost:3000/
curl --fail --silent --show-error http://localhost:3000/trpc/healthCheck
```

分别应看到 `OK`，以及含 `"result":{"data":"OK"}` 的响应。

然后在浏览器完成：注册或登录 → 进入后台 → 查询／保存一条 GitHub 用户资料 → 刷新后数据仍存在 → 退出登录。

健康接口只验证接口服务，不能单独证明数据库认证、表结构和登录会话都正常。GitHub 用户查询需要互联网；GitHub 匿名接口限流也可能导致查询失败。

Chrome 按 `Command–Option–I` 打开开发者工具，在 Network 中核对请求指向 `localhost:3000`，没有误用 AWS 生产 API。

## 5. 本地数据库怎么查看

在仓库根目录、新终端运行：

```sh
pnpm -F @sl-ai-admin/db exec prisma studio
```

打开终端输出的 Studio 地址，就能查看账号、会话、GitHub 用户资料等表。它是可选的数据库管理界面，不是前后端启动的前提。

需要用 `psql` 时可交互连接：

```sh
psql -h localhost -p 5432 -U postgres -W -d sl_ai_admin
```

用户名和库名仍以你的实际本地配置为准。进入后：

```sql
\dt
\q
```

`\dt` 查看表，`\q` 退出 psql。无需启动 AWS 跳板机来查看本地数据库。

## 6. 代码修改后要做哪些操作

| 修改类型 | 需要做什么 |
| --- | --- |
| Web 页面／组件 | 保存后在浏览器看热更新，必要时刷新 |
| 后端路由／业务逻辑 | 保存后等待 `tsx watch` 重启，重新发请求 |
| `.env` 或启动配置 | 停止并重启对应服务；Web 的公开环境变量也需要重新加载 |
| 依赖／锁文件 | `pnpm install --frozen-lockfile` 后重启服务 |
| 拉取到新的 Prisma 迁移 | `pnpm db:generate`，再 `pnpm -F @sl-ai-admin/db exec prisma migrate deploy` |
| 自己改数据库 schema | 在本地创建 migration，再生成 Prisma Client，最后提交 schema 与 migration |

自己修改 schema 后，示例流程：

```sh
pnpm -F @sl-ai-admin/db exec prisma migrate dev --name describe_your_change
pnpm db:generate
```

`migrate dev` 可能需要数据库角色拥有创建 shadow database 的权限；若提示重置数据库，先检查迁移历史与差异，不要直接确认清空已有数据。

开发期间，本地改动保存只影响本地服务。推送到 main 后才会触发之前配置的云端自动部署。

## 7. 自动化测试怎么跑

### 类型检查与单元测试

依赖和 Prisma Client 已准备好后：

```sh
pnpm -F web exec next typegen
pnpm -F web... -F server... -F @sl-ai-admin/infra check-types
pnpm test
```

范围包括 Web、后端及它们依赖的共享包，并检查 infra；不要求为了 Web 验证去运行移动端构建。

### 浏览器端到端测试（Playwright）

首次安装测试浏览器：

```sh
pnpm -F web exec playwright install chromium
```

运行前确认使用本地开发／测试库，数据库迁移已完成。建议先停止手动启动的前后端，以免测试复用到配置不同的服务：

```sh
pnpm test:e2e
```

Playwright 会自行启动后端 `3000` 和前端 `3001`，测试结束后关闭它启动的服务；数据库仍需提前运行。如果这两个端口已经有服务，当前配置会尝试复用。

这些用例会写入测试账号与业务记录，结束时清理 `e2e_` 前缀的临时用户、关联资料，以及共享 `test` 账号的会话。需要保留纯净开发数据时，请先准备独立本地测试库，让 server 与 Prisma 都使用该测试库，再启动测试；不要连接云端生产库。

共享测试账号为 `test / test1234`，由 E2E 初始化在不存在时创建，不代表刚装项目就已经有这个账号。

定位问题可使用带浏览器窗口的方式：

```sh
pnpm -F web exec playwright test --headed
```

失败时看终端具体用例、`apps/web/test-results/` 中的 trace。首次 Next.js 路由编译会较慢；GitHub 用户查询的真实外部请求还可能受到匿名 API 额度影响。

## 8. 结束开发怎么停止

| 对象 | 停止方法 |
| --- | --- |
| 前端 `pnpm dev:web` | 在该终端按 `Control–C` |
| 后端 `pnpm dev:server` | 在该终端按 `Control–C` |
| Prisma Studio | 在对应终端按 `Control–C` |
| Homebrew PostgreSQL | 通常可留在后台；想停止时用 `brew services stop postgresql@17` |

关闭浏览器页面不等于停止前后端。停止 PostgreSQL 不会删除数据库文件，下次启动后数据仍在。

## 9. 可选：使用 Docker 数据库

你已经有 Homebrew PostgreSQL，通常不需要本节。若要为新环境单独建一个 Docker 本地库，先打开 Docker Desktop 并确认 `docker info` 正常。

为避免占用现有 `5432`，下面使用本机 `5433`。首次创建：

```sh
docker run -d \
  --name sl-ai-admin-postgres \
  -p 127.0.0.1:5433:5432 \
  -e POSTGRES_USER=sl_ai_dev \
  -e POSTGRES_PASSWORD=sl_ai_dev_only \
  -e POSTGRES_DB=sl_ai_admin \
  -v sl-ai-admin-pg17:/var/lib/postgresql/data \
  postgres:17
```

`sl_ai_dev_only` 仅为本机示例开发密码，不用于云端或共享环境。Apple Silicon 使用默认匹配平台即可，不需要加 AWS 镜像构建时的 `--platform linux/amd64`。

采用这一方案时，`apps/server/.env` 中对应改成：

```dotenv
DATABASE_URL=postgresql://sl_ai_dev:sl_ai_dev_only@localhost:5433/sl_ai_admin
```

再生成 Prisma Client、应用迁移并启动服务。之后每天只需：

```sh
docker start sl-ai-admin-postgres
pg_isready -h localhost -p 5433
```

停止数据库用 `docker stop sl-ai-admin-postgres`。命名 volume 保存数据，不要为了日常启动删除容器卷。`POSTGRES_USER`、`POSTGRES_PASSWORD`、`POSTGRES_DB` 只在空数据目录首次初始化时生效，改这些参数不会自动修改已有库的用户密码。

## 10. 常见问题

| 现象 | 处理顺序 |
| --- | --- |
| `command not found: pnpm` | 安装 pnpm 固定版本，重开终端 |
| `pg_isready` 显示 `no response` | 确认选用 Homebrew 还是 Docker，启动对应服务并核对端口 |
| Homebrew 命令在当前 macOS 上崩溃 | 项目历史上发生过旧 Homebrew 不兼容；先检查并更新 Homebrew，再重试 |
| 数据库连接被拒绝 | 核对本机主机、端口、用户、密码及库名；`accepting connections` 不等于密码正确 |
| `ERR_MODULE_NOT_FOUND ... prisma/generated/client` | 先运行 `pnpm db:generate`，再重新启动后端 |
| 表不存在、接口返回 500 | 先确认本地连接，再应用仓库已有迁移 |
| `BETTER_AUTH_SECRET` 校验失败 | 本地密钥至少 32 字符，保存在 server `.env` |
| 登录后又回到登录页 | 检查后端是否启动、本地 `NEXT_PUBLIC_SERVER_URL`、是否残留 `AWS_API_ORIGIN`、Cookie 和服务端会话请求 |
| 注册／登录报跨域错误 | Web 固定用 `localhost:3001`，后端 `CORS_ORIGIN` 与它一致；不要混用 localhost 与 127.0.0.1 |
| 前端自动换到 `3002` | `3001` 已被占用；先找出旧服务并正常停止，再用 `3001` 启动，否则与 CORS 和 E2E 配置不一致 |
| `EADDRINUSE` | 用下面的只读命令检查占用，再到对应终端按 Control–C；不要直接杀掉不认识的进程 |
| Turbo 显示交互任务无法运行 | 用文档中的 `pnpm -F @sl-ai-admin/db exec prisma ...` 直接命令 |
| Prisma 询问是否安装 agent skills | 这是可选开发工具提示，不是数据库错误，不影响生成客户端 |

查看端口占用：

```sh
lsof -nP -iTCP:3000 -sTCP:LISTEN
lsof -nP -iTCP:3001 -sTCP:LISTEN
lsof -nP -iTCP:5432 -sTCP:LISTEN
```

## 11. 和云端部署的区别

| 项目 | 本地开发 | 云端生产 |
| --- | --- | --- |
| 页面 | Next.js 开发服务，`localhost:3001` | Cloudflare Worker |
| 后端 | Hono Node 服务，`localhost:3000` | AWS Lambda + API Gateway |
| 数据库 | 本机 PostgreSQL 或本机 Docker PostgreSQL | Aurora Express |
| 接口配置 | `NEXT_PUBLIC_SERVER_URL=http://localhost:3000` | 同源代理 + `AWS_API_ORIGIN` |
| 数据库登录 | 本地用户密码 | AWS IAM + TLS |
| 启动 | 两个终端保持运行 | Git 自动发布后的托管服务 |
| 账号数据 | 存在本地数据库中 | 存在云端数据库中，不自动同步 |

只查看本地效果，不需要执行 CDK deploy、Wrangler deploy 或 AWS login，也不需要创建 VPC、跳板机、Aurora。
